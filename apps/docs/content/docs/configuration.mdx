# Configuration

muxa is designed to work with zero configuration, but understanding how it detects and works with your project structure can help you get the most out of it.

## Zero Config Philosophy

muxa requires no configuration files. It automatically:

- Detects your package manager (npm, yarn, pnpm, bun)
- Finds workspace packages in monorepos
- Handles different monorepo structures
- Wraps commands appropriately

## Settings

Settings are optional values under the `muxa` key of the `package.json` in the folder you run muxa from; muxa does not look in parent folders. Your commands stay self-contained: Settings change how muxa shows processes, never what runs.

```json
{
  "muxa": {
    "mouseScrollSpeed": 1,
    "processListTitle": "Dev"
  }
}
```

| Key                | Value                     | Default                                    | Effect                                              |
| ------------------ | ------------------------- | ------------------------------------------ | --------------------------------------------------- |
| `mouseScrollSpeed` | Whole number of 1 or more | 5                                          | Lines to scroll per mouse or touchpad scroll event. |
| `processListTitle` | Non-empty string          | `name` in `package.json`, else folder name | Heading above the process list.                     |

An unknown key or a bad value stops muxa before any process starts, with an error that names the key; for an unknown key, it also lists the known ones.

muxa passes `mouseScrollSpeed` to dekit in a temporary config file, deleted when muxa exits; after a `SIGKILL`, it stays in the system temp directory. dekit then ignores a `mprocs.yaml` in the same folder, which it reads otherwise. Your global mprocs config (`~/.config/mprocs/mprocs.yaml`) still applies for anything Settings do not set, such as the width of the process list.

## Package Manager Detection

`-s` runs scripts with the package manager your project uses. muxa checks at startup, in the folder you run it from, and takes the first match:

1. A lockfile, in this order:
   - `bun.lockb` → `bun run <script>` (muxa does not read `bun.lock` yet, [issue #39](https://github.com/dendotai/muxa/issues/39))
   - `yarn.lock` → `yarn run <script>`
   - `pnpm-lock.yaml` → `pnpm run <script>`
   - `package-lock.json` → `npm run <script>`
2. The `packageManager` field in `package.json`, with a version (`pnpm@8.0.0`)
3. npm

If that package manager is not in your `PATH`, muxa uses npm:

```text
Warning: yarn is not in PATH, so muxa runs scripts with npm.
```

`-c` and `-w` run your command as you wrote it, whatever muxa detected.

## Monorepo Support

muxa reads the workspaces of the folder you run it from, and does not look in parent folders. In a folder without workspaces, `-c`, basic mode and `-s .` work, and `-w` and any other `-s` stop with `No workspace configuration found`.

### npm/Yarn/Bun Workspaces

Either form in `package.json`:

```json
{ "workspaces": ["packages/*", "apps/*", "tools/cli"] }
```

```json
{ "workspaces": { "packages": ["packages/*", "apps/*"] } }
```

### pnpm Workspaces

```yaml
# pnpm-workspace.yaml
packages:
  - "packages/*"
  - "apps/*"
```

When this file exists, muxa does not read `workspaces` in `package.json`. muxa reads one pattern per line, with no comment after it, and no list in brackets.

### Patterns

| Pattern                                  | Packages muxa finds                         |
| ---------------------------------------- | ------------------------------------------- |
| `packages/*`                             | The folders in `packages`, one level deep   |
| `*`                                      | The folders in the folder you run muxa from |
| `tools/cli`                              | That folder                                 |
| `packages/**`, `packages/*/lib`, `{a,b}` | None: muxa does not read these patterns     |
| `!packages/old`                          | Excludes nothing: muxa skips the pattern    |

A package is a folder with a `package.json` that has a `name`. The folder you run muxa from is one too when it has a `package.json`, by the name `.`.

<Callout type="info">Run `muxa workspaces` to see the packages muxa finds.</Callout>

## CI

muxa needs a terminal and a person to quit it: without a terminal it stops with `Error: Stdin is not a tty.` For CI, use a tool that exits with its commands, such as `concurrently`.

## Best Practices

### 1. Monorepo Structure

Organize packages clearly:

```
my-app/
├── package.json
├── apps/
│   ├── web/
│   └── mobile/
├── packages/
│   ├── ui/
│   └── core/
└── services/
    ├── api/
    └── auth/
```

### 2. Naming Conventions

Use clear, consistent names:

```bash
# Good
muxa -s apps/web dev frontend \
     -s services/api dev backend

# Less clear
muxa -s web dev w \
     -s api dev a
```

### 3. Script Organization

Keep related scripts together:

```json
{
  "scripts": {
    "dev": "vite",
    "dev:host": "vite --host",
    "dev:debug": "DEBUG=* vite"
  }
}
```

### 4. Process Dependencies

muxa does not read the dependencies between your packages, and has no [start order](/cli-reference#start). Start a service that others need before muxa:

```bash
docker-compose up -d postgres
muxa -s frontend dev web -s backend dev api
```

## Troubleshooting

### Package Not Found

- Run `muxa workspaces` to see the packages muxa finds
- Check that the workspace [pattern](#patterns) is one muxa reads, and that the package's `package.json` has a `name`
- Use the package's full name or path

### No Workspace Configuration Found

Run muxa from the folder that holds the workspace configuration.

### Script Not Found

- Check the script name against the list in the error
- For a command that is not a script, use `-w` or `-c` instead of `-s`

### Wrong Package Manager

- Run the command with `MUXA_DEBUG=1 MUXA_TEST_MODE=true` to see the [detected package manager and the command](/cli-reference#debugging)
- Remove lockfiles of package managers you no longer use
- Check that the package manager is in your `PATH`

### Nested muxa Execution

A script that muxa runs starts muxa itself. Run that script's processes in the first muxa command.

### A Key Does Nothing

The output has focus, so the key goes to the process: see [Keys](/cli-reference#keys).

### No Colors

A tool that ignores [`FORCE_COLOR`](/cli-reference#environment-variables) needs its own color flag.
