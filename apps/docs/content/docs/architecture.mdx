# Architecture

Understanding how muxa works under the hood.

## Overview

muxa is built as a wrapper around [dekit](https://github.com/pvolok/dekit), the next version of mprocs, in its own mode, providing:

1. **Simple CLI interface** - Intuitive command-line syntax
2. **Workspace awareness** - Native monorepo support
3. **Intelligent wrapping** - Automatic shell handling
4. **Zero configuration** - Works out of the box

## Core Components

### Command Parser

Reads the arguments of basic mode and of `-c`, `-s` and `-w` by position ([Options](/cli-reference#options)). muxa parses them itself, with no CLI framework, because a flag takes several arguments.

### Workspace Resolver

Finds the packages of npm, Yarn, pnpm and Bun workspaces ([Monorepo Support](/configuration#monorepo-support)), and the package a command names ([Package Resolution](/cli-reference#package-resolution)).

### Package Manager Detection

Picks the package manager that runs scripts ([Package Manager Detection](/configuration#package-manager-detection)).

### Command Builder

Turns the arguments into the tasks of a `dekit.yaml`, which muxa writes in `.muxa/<title>/`, where `<title>` is the process list title:

```bash
# User input, with yarn.lock present
muxa -s backend dev api -w mobile 'npx expo start'
```

```yaml
# .muxa/myapp/dekit.yaml
"tasks":
  "api":
    "label": "api"
    "cmd": "yarn run dev"
    "cwd": "/path/to/packages/backend"
    "autostart": true
    "log":
      "file": "/path/to/.muxa/logs/api.log"
      "mode": "append"
  "mobile":
    "label": "mobile"
    "cmd": "npx expo start"
    "cwd": "/path/to/apps/mobile"
    "autostart": true
    "log":
      "file": "/path/to/.muxa/logs/mobile.log"
      "mode": "append"
```

A folder with no `package.json` keeps this folder in `~/.local/state/muxa/runners/`.

## Technical Design

### Why dekit?

dekit provides:

- **Terminal multiplexing** - One terminal per process
- **Interactive support** - Each process has its own pseudo-terminal
- **Clean output** - No interleaved logs
- **Process management** - Start, stop and restart from the process list

### Process Execution Flow

1. **Parse** - Read the command-line arguments
2. **Resolve** - Find the workspace packages and the package manager
3. **Build** - Generate the `dekit.yaml`, with commands [wrapped in `sh -c`](/cli-reference#shell-wrapping) where needed
4. **Check** - Validate Settings, and ask about duplicate names
5. **Log** - Add the start line to each [log file](/usage#log-files)
6. **Execute** - Run `dekit up`, `dekit reload --yes` and `dekit attach`; after the screen closes, stop the runner

## Performance Considerations

muxa starts the dekit binary (Rust) directly. A hidden task in the same runner checks the [sizes of the log files](/configuration#log-size-limits) once per second, for as long as the runner runs.

## Security Considerations

### Command Injection

- Commands run as you wrote them, with your user's rights
- muxa does not check what a command does
- Same security model as direct shell usage

### File System Access

- Reads `package.json` files, `pnpm-workspace.yaml`, the names of lockfiles, and `~/.config/muxa/settings.json`
- Writes the [log files](/usage#log-files), with a `processes.json` and a `.gitignore` beside them, the temporary copy that [`muxa logs`](/cli-reference#logs-process) prints, and the `dekit.yaml` of the processes in `.muxa/<title>/`

## Comparison with Alternatives

### vs Direct dekit or mprocs

muxa adds:

- Simpler syntax
- Workspace support
- Automatic detection
- No config files

### vs concurrently

muxa provides:

- Better output formatting
- Interactive features
- Monorepo awareness
- Cleaner syntax

### vs turbo/nx

muxa focuses on:

- Process running, not building
- Zero configuration
- Universal compatibility
- Simple interface

## Maintaining Simplicity

Core principles:

- Zero config by default
- Simple things stay simple
- Advanced features are optional
- Backward compatibility

## Contributing
